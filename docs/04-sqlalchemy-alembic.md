# SQLAlchemy & Alembic: Python ⇄ database, and safe change

**In one sentence:** SQLAlchemy lets you work with database rows as Python objects; Alembic records every schema change as a small, ordered, reversible script.
**Hands-on:** notebook `03_sqlalchemy_and_alembic` · **Real code:** `backend/app/models/`, `backend/app/db/`, `backend/app/services/`, `backend/alembic/`

## Mental model
* **Model class** = a table's blueprint.
* **Session** = a shopping basket + notepad. You `add()` things, it remembers what changed, and `commit()` writes everything in one transaction.
* **Alembic** = **git for your schema**: each migration is a commit; `upgrade` moves forward, `downgrade` goes back.

## Models (2.0 style)

```python
class Ticket(Base):
    __tablename__ = "tickets"
    id: Mapped[int] = mapped_column(primary_key=True)
    title: Mapped[str] = mapped_column(String(200))
    assignee_id: Mapped[int | None] = mapped_column(ForeignKey("users.id", ondelete="SET NULL"))
    assignee: Mapped["User | None"] = relationship()          # follow the link as an object
    tags: Mapped[list[Tag]] = relationship(secondary=ticket_tags, lazy="selectin")
```
`Mapped[int]` is the Python type; `| None` makes the column nullable.

## Querying (2.0 style)

```python
stmt = select(Ticket).where(Ticket.status == "open").order_by(Ticket.id.desc()).limit(20)
tickets = (await db.scalars(stmt)).all()         # list of Ticket objects
one     = await db.get(Ticket, 5)                # by primary key (uses the identity map)
count   = await db.scalar(select(func.count(Ticket.id)))
# (the snippets in notebook 03 use the plain sync Session; TeamDesk's API uses AsyncSession: every DB call is awaited)
```

## Session lifecycle

| Call | Meaning |
|---|---|
| `db.add(obj)` | put in the basket (no SQL yet; **not** awaited) |
| `await db.flush()` | send SQL **inside** the open transaction (IDs get assigned) |
| `await db.commit()` | make it permanent |
| `await db.rollback()` | discard everything since the last commit |
| `await db.refresh(obj)` | reload from the database |
| `async with db.begin_nested():` | a SAVEPOINT: undo only part |

**Identity map:** within one session the same row is always the *same Python object*.
**Unit of work:** change several objects, then one `commit()` writes them atomically. TeamDesk does this so the **ticket change and its audit row commit together**.

### In FastAPI
`get_db` (an async generator) yields one `AsyncSession` per request and always closes it. Services call `await db.commit()` themselves at the end of an operation; routes never touch transactions.

## The N+1 problem (the #1 ORM trap)

```python
for t in db.scalars(select(Ticket)):      # 1 query...
    print(t.requester.full_name)          # ...+ 1 query PER ticket  = N+1
```
Fix by **eager loading** (notebook 03 measures it: 11 queries → 2 → 1):

| Relationship type | Use | Result |
|---|---|---|
| many-to-one (ticket → requester) | `joinedload(Ticket.requester)` | one `JOIN` |
| one-to-many / many-to-many (ticket → tags) | `selectinload(...)` or `lazy="selectin"` | one extra `IN (...)` query |

Spot it: Logfire shows dozens of identical `SELECT` spans under one request.

## Alembic workflow

```bash
# 1. change a model
make revision m="add due_date to tickets"     # alembic revision --autogenerate -m "..."
# 2. READ the generated file in backend/alembic/versions/ (autogenerate is a draft!)
make migrate                                  # alembic upgrade head
# 3. commit model change + migration file together
```

| Command | What it does |
|---|---|
| `alembic upgrade head` | apply all pending migrations |
| `alembic downgrade -1` | undo the last one |
| `alembic current` / `history` | where am I / list all |
| `alembic check` | fails if models and DB differ (great in CI) |
| `alembic upgrade head --sql` | print SQL instead of running it (for a DBA to review) |

How it works: a table `alembic_version` stores the current revision id. Each migration file has `upgrade()` and `downgrade()` and a `down_revision` pointing to its parent: a linked list.

### Naming convention
`db/base.py` gives every constraint a predictable name (`uq_users_email`, `fk_tickets_requester_id_users`). Without names, Alembic can't reliably alter or drop them later.

### Safe-migration rules
1. **Never edit** a migration that has been applied elsewhere. Add a new one.
2. **Read autogenerated output.** A *rename* looks like *drop + add* (data loss!). Fix with `op.alter_column(..., new_column_name=...)`.
3. New `NOT NULL` column on a big table: add **nullable** → backfill → set **NOT NULL** (three steps).
4. Keep changes **backward compatible for one release** (add first, remove later) so you can roll the app back.
5. Run migrations **before** the new code starts (TeamDesk's entrypoint does).
6. Test `upgrade` → `downgrade` → `upgrade` on a scratch database (notebook 03 does exactly this).
7. Large data backfills belong in a **separate script/job**, not inside a migration transaction.

## Best practices
* One session per request; never share a session across threads.
* `expire_on_commit=False` for web apps (objects stay readable after commit).
* `pool_pre_ping=True` to survive DB restarts; size the pool to your workers × threads (`pool_size`, `max_overflow`).
* Use `select()` + `db.scalars()`; avoid raw SQL unless needed, and then bind parameters.
* Add `ORDER BY ... , id` tie-breakers so pagination is stable.
* Use bulk `update()`/`delete()` statements instead of loading thousands of objects.
* Keep queries in the service layer, not in routes.

## Common mistakes
| Mistake | Fix |
|---|---|
| N+1 queries | eager loading (above) |
| Using `create_all()` in production | migrations |
| Catching `IntegrityError` without `rollback()` | session stays unusable until you roll back |
| Lazy loading after the session closed (`DetachedInstanceError`), or at all in async code (`MissingGreenlet`) | eager-load what you need (`joinedload` / `selectinload` / `lazy="selectin"`) |
| Returning ORM objects without a response model | leaks columns; always use a schema |
| Check-then-insert race | rely on the `UNIQUE` constraint, handle the error (see `create_user`) |

## Async (what TeamDesk uses)
The API uses `create_async_engine`, `async_sessionmaker(expire_on_commit=False)`, `async def` routes and `await db.execute(...)`, with the same `postgresql+psycopg://` URL. Three rules: **await every DB call**, **no lazy loading**, **`expire_on_commit=False`**. One session = one connection = one statement at a time, so queries that should overlap each use their own session.
Full explanation: [14-async-and-parallelism.md](14-async-and-parallelism.md) and notebook 09. **Alembic stays synchronous**; see [ALEMBIC.md](ALEMBIC.md).
